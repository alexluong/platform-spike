## Design: what Zitadel owns

| concern | where it lives in a2 | mechanism |
|---|---|---|
| merchant | Zitadel organization, **id = merchant id** | `AddOrganization{organizationId}` from the `merchant.created` outbox row (idempotent: a retry gets `already_exists`); the platform project is granted to it (`CreateProjectGrant`, role `member`) |
| platform staff, apps | the platform org (first-instance org, owns the project) | as in a |
| customers | org `customers` | users created there |
| merchant users before they join | org `people` | users created there |
| membership | an **authorization** (user grant) on the platform project, created in the merchant's org, role `member` | `member.added` / `member.removed` outbox rows (direct add, invitation accept, merchant create's owner) |
| agents | machine users **inside the merchant's org** | created by the agents module through the port, disabled until `agent.registered` commits |
| login policy (§15.3) | project setting "check authorization on authentication" (`projectRoleCheck`) + org state | below |
| invitations (§15.2) | **app-side** table `invitations` | Zitadel's invite codes onboard a new user into an org; the spec's invitee already exists |
| roles, assignments, limits, guardrails | app DB + SpiceDB, as in a | unchanged |
| tenant claim in tokens | `urn:zitadel:iam:org:project:roles` → `member: {<merchant org id>: …}` (users, after they joined); `urn:zitadel:iam:user:resourceowner:id` (agents) | an extra check in the authenticator, never the source |

**A Zitadel user lives in exactly one organization and cannot be moved** (no move API in v4.19.4: checked the v2 user/org protos). The spec's merchant users exist before they join (the suite creates and logs them in first, then adds them or invites them), so "members are users in the merchant's org" can't hold for them. Choices considered:
- create the user in a holding org and move it on join: no API;
- re-create it in the merchant org on join: needs the password (or its hash, which the API doesn't return) and changes the `sub`, breaking the token issued earlier;
- **cross-org authorization (chosen):** Zitadel's own B2B model (project grant to the customer org, the customer org authorizes users). The user stays in `people`; the merchant org holds the authorization. Membership is visible in Zitadel per merchant (`ListAuthorizations` by org), the token names the merchant org, and the org can be used for login policy.

Users who'd sign up through a merchant's own invitation of a new email would be created in the merchant org directly (not built: the spec's invitee exists).

**Login policy.** The project requires an active authorization to log in. Every human gets an `account` authorization from the platform org when created (test endpoint). Suspending a merchant:
1. deactivates its organization: its agents (resident machine users) get no tokens;
2. deactivates every authorization of its members on the project (their `member` authorization and their `account` authorization): their next login is refused at the auth-request step (`Errors.User.GrantRequired`).

Step 2 is needed because **Zitadel doesn't cascade an org's deactivation to the authorizations it handed out**: the login check (`app_oidc_project_permission.sql`) looks only at the authorization's own state, not at the granting org or the project grant, so deactivating the project grant wouldn't help either (from the query; not tried). So suspension is a fan-out over the members, as it would be with per-user deactivation; the org only covers what lives in it.

### Suspension: what Zitadel actually does

Read in the v4.19.4 source, then checked against the running stack.

| case | behaviour | when | checked by |
|---|---|---|---|
| member logs in | refused at "finalize auth request" (`GrantRequired`) | as soon as the authorization projection shows the deactivation; the sync waits for it, so **before suspend answers 200** | suite |
| agent `client_credentials` | refused (`Errors.User.NotActive`): the event-store check of the user's org at token creation | immediately | suite |
| access tokens issued before | still valid JWTs until `exp` (12 h default); the app answers 403 `merchant_suspended` from its DB | n/a | suite |
| member's refresh token | **still works**: a refresh checks the user's *home* org (`people`) and the user's state, not authorizations. The new access token simply lacks the `member` claim | n/a | probe (a second OIDC app with the refresh grant, ad hoc) |
| resident user's refresh token (an org-resident user) | refused if the org was deactivated after it was issued, **even after reactivation** (`checkOrgNotDeactivatedAfter`) | immediately | source only |
| reinstate | org activated, authorizations reactivated; login and agent tokens work on the next try | the sync waits for the org and authorization projections | suite |
| token issuance after reactivating | also reads user and org state from the **userinfo projection** (`org_state = 1`, `u.state = 1`); until it catches up: 404 `User.NotFound` | projection lag (tens of ms) | observed (the first-run failure) |

So Zitadel checks org state in three places (event store at token creation, userinfo projection at issuance, refresh-token history), and authorizations in one (the auth-request step, from a projection). The app's 403 `merchant_suspended` remains the only check that covers refresh tokens and already-issued tokens.

## Cross-system writes (§15.1): the IdP as a second outbox consumer

Zitadel calls can't join the app's transaction. Every write that spans both goes through the outbox:
- An event is written **once per consumer** that takes it, in the request's transaction (`outbox.consumer`). The authz engine takes every event (as before); the identity sync takes `merchant.created`, `merchant.suspended`, `merchant.reinstated`, `member.added`, `member.removed`, `agent.registered`.
- The identity consumer is **partitioned per merchant** (`outbox.partition_key`, an advisory lock per merchant): order holds per merchant; a stuck row blocks only its merchant. A global queue serialized every Zitadel call behind every other merchant's (each 20–60 ms; the suite makes ~1400 identity rows), and every write request waits for its own drain. The authz consumer stays global, as in a.
- Same rules as the SpiceDB relay: transient errors are retried forever in order (1 s loop + the request's own drain); only `invalid_argument`/`unimplemented` are dead-lettered. Every handler is idempotent (`already_exists`, "already active/inactive" and `not_found` on delete count as done).
- **Read-your-writes for login:** after a Zitadel write the sync waits (up to 10 s, then a transient error) until Zitadel's projections show it, because the login check reads projections. So when suspend/reinstate answer, the next login already sees it.

The other design, IdP as the single writer with app state derived from it, was rejected: the tenant precheck, the one-merchant rule and the last-owner/assign row locks run in SQL in the request's transaction; reading membership from Zitadel per request means an HTTP call against an eventually consistent projection and no locks.

| write | what happens in Zitadel | failure window (Zitadel down or slow) | effect on access |
|---|---|---|---|
| merchant create | org + project grant (outbox) | the merchant exists in the app, not in Zitadel, until the relay applies it | none on the API. Agent registration fails (500) until the org exists; members' `member` authorizations queue behind it |
| member add / invitation accept / owner at create | `member` authorization (outbox) | Zitadel's membership lags | none: membership is read from the app DB; login uses the `account` authorization; the token's tenant claim is missing meanwhile |
| member remove | delete `member` authorization (outbox) | stale membership in Zitadel | none: the app denies on the next request. The stale claim can't matter (it names a merchant the user no longer belongs to; the check fires only when the user belongs to a different one) |
| suspend | org + members' authorizations deactivated (outbox) | **the merchant's people and agents can still log in and get tokens**; every request is 403 `merchant_suspended` from the DB. The request answers 200 even if its drain failed (§14 P6) | fail-open at the IdP, closed at the API |
| reinstate | activate org + authorizations (outbox) | nobody of that merchant can log in until applied | fail-closed |
| agent register | machine user created in the merchant org **before** the insert (the response needs the secret), immediately deactivated; `agent.registered` (outbox) re-activates it | tx rolls back: an inert, deactivated machine user stays (no tokens). Enable row pending: the agent can't get tokens yet | fixes review-a #12 for agents; a sweep of deactivated machine users with no `agents` row would remove the leftovers (not built) |
| app register | unchanged from a (active machine user before the insert) | orphan on rollback (review-a #12 still open for apps) | an orphan's tokens map to no principal (401) |
| test user create | user + `account` authorization before the insert (test endpoint only) | orphan Zitadel user on rollback | none |

Cross-partition ordering: a user's events in two merchants (removed from one, joining another) are in two partitions. They touch different authorizations, except that `member.removed` re-activates the `account` authorization if it is inactive. That only matters when someone is removed from a suspended merchant, which the API refuses (the merchant's people are locked out). Recorded, not handled.

## Custom roles: Zitadel's roles not used for §3

Zitadel's project roles are flat keys per project; a project grant can pass a subset of them to an org, and an authorization holds keys. There is no store scope, no per-assignment object (409 `already_assigned`, delete by id), no refund limit, no "you can only hand out what you hold" guardrail, and no way for a merchant to define a role (roles are defined on the project by the platform). §3 stays in the app DB and SpiceDB. The two role keys a2 uses (`account`, `member`) are login entitlements and the tenant claim; no §3 role is kept in two places.

**Nothing Zitadel-specific reached a module.** The modules emit IdP-neutral facts and pass the kind and merchant to the port; with `IDP=zitadel` (stack a) the new events go only to the engine, which ignores them. Two port-level findings:
- **The outbox event type lives in the `authz` package**, so the identity adapter imports the authz port to consume events. With two kinds of consumer it belongs in its own package.
- **The port leaks a timing contract:** "an agent's client may stay disabled until `agent.registered` is applied". Modules must emit that event for the IdP's sake. It is neutral (a fact, not a call), but it is a rule a new module author must know.

## What Zitadel's organizations gave (that Ory OSS can't)

- **Tenants with a lifecycle enforced at token issuance.** Deactivating an org stops tokens for everything inside it, client_credentials included, immediately (event-store check). In b, Kratos and Hydra have no tenant object: a suspended merchant's agents could only be stopped by deleting or rotating each Hydra client, and its users by a login/consent-app check written by us.
- **Login-time authorization ("check authorization on authentication")**: the IdP refuses the login itself, which is what §15.3 asks for. Ory OSS has no equivalent; Hydra's login/consent app is the place, i.e. app code.
- **Cross-org authorizations with project grants**: per-merchant membership stored and listable in the IdP, with the granting org in the token's role claim (a tenant claim for free). Ory OSS has no organizations (Ory Network's organizations are for B2B SSO, not membership).
- **Org-scoped machine users**: an agent belongs to its merchant in the IdP, so suspension reaches it without an app-side list.

What it pushed back into the app: the identity sync consumer (outbox routing, partitions, idempotent handlers, error classification), projection waits for read-your-writes, home orgs and the `account` authorization for every human, the per-member fan-out on suspend/reinstate, and invitations.

## Token checks (SPEC §14 P7, done for a2 and therefore a)

`zitadel.Verify` now checks: signature with an RS256-only allowlist, `iss`, `aud` contains the project, `exp` (go-oidc); **an access token, not an ID token**: Zitadel's access tokens carry `client_id` and none of the ID-token claims `at_hash`, `nonce`, `azp`, `amr` (both have header `typ: JWT`, so the header can't tell them apart); **the client is allowed**: the login app's client id, or a machine user this app provisioned (client_credentials tokens put the machine's username in `client_id`; ours start with `app_`/`ag_`). Checked live: the ID token from the same login → 401; a token from a second OIDC app in the same project → 401; access tokens, app and agent tokens → 200. Stack a's 362 tests pass with it.

Weak spot: the machine-client rule is a username prefix. The precise check compares the token's `client_id` with the `client_id` stored on the app or agent row; that needs `client_id` in `identity.Token` and a line in `LookupPrincipal`.

The tenant claim (`Token.MerchantID`) is checked only when both the token and the caller have a merchant. The suite never trips it (no test moves a user between merchants with an old token).

## DX notes

- **What was hard:** finding out what "deactivate organization" covers. The doc comment says "Users of this organization will not be able to log in". True, for users *resident* in it. Cross-org authorizations, project grants and refresh tokens of those users are untouched. Only the source (`internal/command/user_auth.go`, `org_auth.go`, `query/app_oidc_project_permission.sql`, `query/userinfo_by_id.sql`) shows which check reads what, and from where (event store vs projection).
- **No user move**, and the docs don't say so; the B2B guide assumes users are created in their org. For a platform where existing users join tenants, authorizations are the only fit.
- **Eventual consistency is everywhere a test logs in right after a write**: new authorizations, reactivated users and orgs, new machine secrets. Every Zitadel write the next request depends on needs a projection wait in the sync. The waits poll `ListAuthorizations`, `ListOrganizations` and `GetUserByID`.
- **v2 services over Connect** (`POST /zitadel.org.v2.OrganizationService/AddOrganization`, JSON) worked for org, project, authorization and user services. Errors come with a string `code`; `failed_precondition` arrives as HTTP 400, so classify on the code, not the status.
- `AddOrganization` accepts your own id (`organizationId`): merchant id = org id, so the outbox handler is idempotent and the app stores no mapping.
- Access tokens include the role claims with the granting org (`urn:zitadel:iam:org:project:roles`) once the app has `accessTokenRoleAssertion` and the project `projectRoleAssertion`. Inactive authorizations are left out of tokens.
- **What I got wrong first:** `docker exec cat` on the Zitadel image (distroless: read the PAT through a helper container); assuming a just-reactivated machine user could get a token at once (projection); and a first design with one global identity queue, dropped before running it (estimated 60+ s of serialized Zitadel calls per suite run behind write requests).

## Spec issues

1. **§15.1 "members are users in that organization"** can't hold for users who exist before joining, which is what the API and the suite do (no move in Zitadel). a2 uses cross-org authorizations; the org holds the membership record, not the user. A spec for Zitadel-style IdPs would either create the merchant's people through invitations of new emails (then they are resident) or say "membership is the IdP's grant to the user".
2. **§15.3 "its users can't log in"**: holds for new logins. Refresh tokens of cross-org members keep working (Zitadel doesn't re-check authorizations on refresh); the app's 403 covers it. The spec could say "no new session" rather than "no new tokens", or require short-lived refresh.
3. **Accepting an invitation into a suspended merchant** is unspecified; a2 refuses it (403 `merchant_suspended`), as d does.
4. **Invitation statuses** beyond `pending` are unspecified; a2 uses `accepted` and `cancelled`. Accepting a non-pending invitation → 409 `invitation_not_pending`; someone else's → 404.
5. **§14 P6 matters more with an IdP consumer:** a suspend whose identity drain failed answers 200 while the merchant's people can still log in (every request still 403).
