# Stack h2 results: stack h with pools as rows (in-app issuer per pool, zitadel/oidc v3.51.16) + SpiceDB v1.56.2

Stack h (an OpenID provider inside the Go app on `zitadel/oidc` `pkg/op`, state in the app's Postgres) extended to SPEC §16's multi-pool model: pools `workforce`, `platform`, `shop`, and one tenant pool per merchant created in the merchant-create transaction, each its own issuer, with Sign in with Shop as a real OIDC round trip between two pools of the same app. Adapter `go/internal/adapters/oidcpool` (a copy of h's `oidcop`, so h stays runnable), `IDP=oidcpool MULTI_MERCHANT=1`, compose profile `h2`, project `ps-h2`, app on 8098 only. Run 2026-10-19 on cs-ws (load 9–47 on 4 CPUs, other workspaces).

The question: what does it take for our own issuer to carry the multi-pool model, and what does it cost per merchant?

## Design

| choice | what | why |
|---|---|---|
| issuer per pool | `PUBLIC_URL/oidc/<pool id>`: `…/oidc/workforce`, `…/oidc/platform`, `…/oidc/shop`, `…/oidc/pl_<random>` per merchant | One host and one TLS name for every issuer; OIDC discovery works per pool (`<issuer>/.well-known/openid-configuration`); routing is a path prefix any gateway can do. Subdomains need wildcard DNS and TLS; custom domains are a later layer (below). The tenant pool id is not the merchant id, so the directory can remap a merchant (move, rename) without a new issuer string. |
| one provider, many issuers | one `op.Provider`; `route` takes the pool from the path, looks it up in the directory (`idp_pools`, unknown → 404), puts it in `ctx`; the provider's issuer function reads it from there | The library already supports issuer-per-request (`IssuerFromRequest` + `IssuerFromContext`); the identity-model doc listed it as unverified. It works for discovery, JWKS, tokens, userinfo and revocation. Never `Host` / `X-Forwarded-*`. |
| per-pool signing keys | `idp_signing_keys.pool_id`; each pool's JWKS holds only its keys; rotation per pool (`bootstrap rotate-signing-key [pool]`, no pool = all); first key created with the pool, in the merchant's transaction | A relying party that trusts one merchant's JWKS can't be fooled by another merchant's token even if it skips the `iss` check; a merchant's pool can move (cell, export) with its keys and keep its tokens valid; rotation and a leak response stay per merchant. Cost: one row and ~610 B of heap per pool in use. One key ring would be simpler but makes `iss` the only thing separating merchants. Limit: every key is encrypted with the one `ISSUER_SECRET`, so per-pool keys don't shrink the blast radius of a DB + secret compromise. |
| subjects | the identity port's subject is `"<pool>:<sub>"` (built by the adapter from the verified pool) | The app maps a token to a principal only within the pool that issued it, with no core or module change for that rule. Tenant tokens also carry the pool's merchant (from the directory, not a claim); the Authenticator requires it to equal the principal's home merchant. |
| staff vs customers in a tenant pool | one pool, two user groups (`staff`, `customers`), two virtual first-party clients (`merchant-admin`, `storefront`); the login step authenticates only the client's group | SPEC §16.1 "kept apart inside it". Same email as staff and customer = two identities. |
| Sign in with Shop | each tenant pool is a confidential client of the shop pool (`fed_…` row at the shop pool, secret hashed there and AES-GCM-encrypted on the tenant pool row). RP side is `pkg/client/rp` (discovery, code + PKCE, ID token checks with nonce); back channel over HTTP to the app itself (`INTERNAL_URL`, public issuer strings kept) | A real OIDC flow, as if Shop were another company's IdP: the same code would work with Shop in global services and tenant pools in cells. |
| machine clients | apps and agents in the `platform` pool (`client_credentials` there only) | Agents are merchant-owned; putting them in tenant pools would split machine auth across pools for no tested gain. Open. |

## Provisioning (SPEC §16.3, §16.7)

**Atomic with the merchant row.** `POST /api/platform/merchants` runs `ProvisionMerchant` inside the executor's transaction (h's tx-in-ctx): pool row, first signing key, federation client at the shop pool. The response is `201 {status: "active"}`; there is no `provisioning` state. A failure anywhere rolls back everything: no merchant row, no pool, no key, no client. **Failure window: none.** Nothing outside the app's DB is touched, so there is nothing to compensate. `TestProvisioningIsTransactional`: an uncommitted pool is invisible outside the tx, a rollback leaves 0 rows, the issuer of a rolled-back merchant is 404.

| measure | result |
|---|---|
| `POST /api/platform/merchants` from the Mac, sequential, 100 merchants (load ~45) | p50 **34 ms**, p95 **70 ms**, max 92 ms |
| same, 330 merchants at concurrency 4 | p50 95 ms, p95 146 ms |
| `ProvisionMerchant` + commit alone, 500×, over an ssh tunnel to the DB | p50 21 ms, p95 28 ms (four statements' round trips; ECDSA keygen is ~0.1 ms) |
| created per merchant | identity: 3 rows (pool, signing key, federation client); app: merchant, membership, owner assignment, outbox rows |
| DB growth per merchant | `idp_*` tables ~1.7 KB; whole DB ~3.8 KB (over 430 merchants, incl. app rows and the bench's owner users) |
| heap per pool, once used | ~610 B (directory entry + decoded key) + ~1.6 KB (Shop relying party: discovery, key set) ≈ **2.2 KB**; ~1.1 MB at 500, ~22 MB at 10 000 |
| 10 merchants in parallel to `active` (rule 9) | all active in the create response |

## Issuers and keys (SPEC §16.7)

- **The app finds a pool's keys** by reading `iss` unverified, requiring an exact `PUBLIC_URL/oidc/<id>` match and `<id>` in the directory, then verifying with **that pool's keys only** (`poolKeySet`). No JWKS fetch: keys come from the shared DB, cached per pool for 30 s, reloaded on an unknown `kid` (at most every 5 s per pool). Pools nobody uses cost nothing in memory. A pool created on another instance is found at once (a directory miss reads the DB).
- **Rotation per pool:** `bootstrap rotate-signing-key <pool>` (or all pools). Rotating a tenant pool leaves the platform pool's JWKS unchanged (`TestPerPoolRotation`). Rotating 10 000 pools means 10 000 small transactions.
- **A merchant moving cells:** every identity row of a tenant pool is keyed by `pool_id` (pool, keys, users incl. password hashes and federated links, refresh tokens, its federation client at shop), so the pool moves as one unit with the merchant's data, keys included: tokens stay valid, the issuer string doesn't change as long as the gateway routes `/oidc/<pool>` to the merchant's cell. That's simpler than Zitadel's instance export (no passkeys, no machine keys). The platform-level pools stay global. Sign in with Shop already crosses pools over HTTP, which is exactly what a cell → global call would be.

## Shop federation (SPEC §16.7)

- **Wiring:** tenant pool = confidential OIDC client of the shop pool, created with the merchant. Flow: storefront `authorize` at the tenant issuer → `<issuer>/login/shop` (state row + an HttpOnly cookie binding the round trip to this user agent) → shop `authorize` (PKCE S256, nonce) → shop login → `<issuer>/federation/shop/callback` → state claimed once, only with the matching cookie → code exchanged over HTTP at the shop token endpoint, ID token verified by `rp` (signature against the shop JWKS, `iss`, `aud`, `azp`, `exp`, nonce) → tenant identity found or created by `(pool, shop subject)` → the app's `ShopLinker` links its customer record **in the same transaction** → tenant code to the driver.
- **Linking:** by Shop subject, never by email. A local tenant customer with the Shop buyer's email stays a separate, unlinked account (suite rule 7, `TestSignInWithShop`). The merchant's record linked to a Shop account is created by whichever comes first, a Shop-token order or Sign in with Shop, and both reach the same record (unique `(merchant, shop_account_id)`).
- **What the federation client can't do:** its Shop tokens carry `aud` = itself, so the API rejects them; it has no `client_credentials`; it's unknown at tenant pools (`TestFederationClientIsNotAnAPIClient`).
- **Zitadel #9535 (one link per org):** doesn't apply. Links are `(pool, upstream pool, upstream subject)`: one tenant identity per Shop account per merchant, unlimited merchants.

## Security checklist per pool (h's 20 + review-h's 21–23)

Every item that h fixed holds in every pool; pools add one new class of risk, **cross-pool confusion**, and all of it rests on a `pool_id` filter in about 15 queries.

| # | item | h2 |
|---|---|---|
| 1 | issuer from headers | holds per pool: the issuer comes from the directory entry the path named. Probed live: spoofed `Host`, `X-Forwarded-Host`, `Forwarded`, `x-zitadel-instance-host`, `x-zitadel-public-host` → tenant discovery issuer unchanged; the same headers on `/api/me` with a tenant token → same principal |
| 2 | exact redirect match | holds (library); federation clients have exactly one redirect URI (their pool's callback) |
| 3 | PKCE S256 only | holds in every pool (`CreateAuthRequest`), and on the upstream leg |
| 4 | encoded-path bypass | holds; the router refuses any request with an encoded path (`RawPath`), so `/oidc/%70latform/…`, `/oidc/PLATFORM/…`, `/oidc//…`, `../` → 404 |
| 5, 21 | single-use codes; code only to the login POST | holds per pool; **plus:** a code is unknown at any other pool's token endpoint, and presenting it there doesn't burn it at home (`TestTokensStayInTheirPool`). The library callback is closed in every pool (probed: 404). The federation callback answers with the code itself, like the login POST |
| 6 | no machine refresh tokens | holds |
| 7, 8 | key race, rotation, retiring | per pool: creation under `pg_advisory_xact_lock(key, hashtext(pool))`; self-heal per pool; tenant keys created inside the merchant transaction |
| 9 | timing | holds per pool: probed live at a tenant pool, unknown email p50 50 ms vs wrong password 48 ms; federated users (no password) also verify against the dummy hash |
| 10, 22, 23 | rate limits | lockout keys are per pool and group: 10 bad passwords lock that email at M1 only, the same email at M2 still logs in (probed). **Weaker:** the per-IP bucket is shared by every pool on an instance, so one merchant's login burst throttles every merchant behind the same source address (with #23, behind a proxy that is everyone). Production needs limits per pool as well as per IP, and a shared store |
| 11 | revocation | unchanged (stateless access tokens live 15 min); suspension refuses refresh tokens of the pool |
| 12 | ID token as access token | holds; **plus:** each pool accepts only its own clients (tenant: `merchant-admin`/`storefront`; machine clients only in `platform`); forged tokens with M1's key and M2's `iss`, the platform key and a tenant `iss`, a tenant key and the platform client, a trailing `/`, an unknown pool, another host → all 401 |
| 13, 14 | CORS, grants on by default | unchanged; discovery still advertises what isn't served, per pool |
| 15 | keys at rest | per-pool keys and federation secrets, one `ISSUER_SECRET` (see Design) |
| 16 | machine client secrets | unchanged; a secret checks only against its pool and kind |
| 17 | refresh theft | holds per pool; a refresh token is unknown at other pools |
| 18 | hashing as DoS | unchanged; the hash slots are shared by every pool (one merchant's burst queues the others' logins) |
| 19 | login CSRF / sessions | still open for the password step; Sign in with Shop adds the first browser binding (state + cookie), the piece a login page needs |
| 20 | test mode | `GET /api/_test/login-hint` (TEST_MODE only) says which platform-level pool an email lives in, because the core driver's `loginUser` has no pool argument |
| new | pool from unverified `iss` | an unknown pool-shaped `iss` costs one indexed DB read before the signature check (directory miss, not negatively cached) |
| new | cross-pool confusion | codes, auth requests, refresh tokens, clients, users, keys, revocation and userinfo are all filtered by the request's pool; outside a pool route the pool is `""`, which matches nothing. A missed filter would mint a token for another merchant's user. Today it's tested per object type; in production it wants a lint or a query layer that can't forget it |
| new | federation | state single-use, cookie-bound (a wrong cookie doesn't burn it), pool-bound (an M1 callback at M2 → 400), nonce checked; back channel only to the shop issuer (no caller-controlled URL) |

**Library and our own bugs found:** the library copies `SetUserinfoFromScopes`' result over the ID token's claims, so an empty implementation sends ID tokens **without `sub`**. Stack h has this bug today (nothing read its ID tokens); h2's Shop leg did. And `rp`'s default ID-token verifier rejects any nonce unless `WithNonce` is set.

## What custom store domains would take (not built)

- A verified-domain table (`host → pool`, status, verification token) and the issuer per pool from it: `https://shop.brand.com/oidc` (or `/account`) instead of `PUBLIC_URL/oidc/<pool>`. `route` resolves the pool from **(Host, path) against verified domains only** (an unverified Host → 404, never a derived issuer); `Verify` maps `iss` → pool through the same table.
- Several stores of one merchant share one pool (customers belong to the merchant), so a pool needs several issuer aliases: tokens carry the alias the login used, and the verifier accepts any verified alias of that pool. Federation redirect URIs per alias (the shop pool's client gets one redirect per domain).
- TLS per domain at the edge (ACME), cookies scoped per domain, CORS per storefront origin. **Passkeys bind to the RP ID (the domain)**: a merchant changing or adding domains would strand passkeys registered under the old one unless the RP ID stays on a platform domain. Decide that before passkeys ship.
- Zitadel does the equivalent with `x-zitadel-public-host` plus registered instance domains; h2 needs ~a table, a resolver branch and the alias rule in `Verify`.

## Staff invitation flow (not built)

What h2 would need for real: an `idp_invitations` row per tenant pool (email, group `staff`, token hash, expiry, inviter), email delivery with a rate limit, an accept page that verifies the token (= verified email) and sets the credential. With email codes + passkeys as the production methods (identity-model.md §9): a one-time-code table per pool and WebAuthn (`go-webauthn`, credentials per pool, RP ID per issuer domain). The app's membership is created on accept, **in the same transaction** as the identity, which is h's advantage again: no "identity created, member not added" window. Platform accounts invited as partners don't need any of this (they already have an account; §15.2's app-side invitations cover them).

## DX notes

1. **One provider, many issuers works**, but nothing documents it: the issuer function must read a pool the caller put in `ctx` before the library's router, and the library's own verifiers (userinfo, `id_token_hint`) need a key set that reads the pool from `ctx` too.
2. **Every storage method needs the pool** (about 15 queries). The library gives storage only `ctx`; forgetting one filter is a cross-tenant bug that no protocol check catches.
3. **`SetUserinfoFromScopes` overwrites the ID token's `sub`** (see above).
4. `rp`: the default nonce check rejects every nonce until `WithNonce` is set; `rp.WithURLParam` returns a `URLParamOpt`, which `AuthURL` doesn't take without a conversion; `go mod tidy` pulls a new indirect dependency (`google/uuid`).
5. Compose profile name clash: stack h already used `h2` for its second instance.
6. Ops trap: an ssh tunnel to a container IP keeps pointing at that IP after `down -v`, by then possibly another project's Postgres. Re-resolve after every recreate.
7. The cs-ws dev proxy (rewrites `localhost` in redirects on 8090+) didn't interfere: every redirect names `cs-ws.lab.alexluong.com` or the `127.0.0.1` loopback client. No collielab change.
8. What the agent got wrong first: the empty-`sub` ID token (found by the suite's first Shop test), the nonce default, and a federation state burned by a wrong cookie (fixed: the cookie hash is part of the claim's `WHERE`).

## Verdict

- **The model fits our own issuer with little code.** +608 lines in the adapter (+62 %) carry pools, an issuer per pool, per-pool keys, atomic provisioning, pool-level suspension and Sign in with Shop over real OIDC. 401/401, first full run after one library fix.
- **A merchant costs ~nothing**: three rows, ~1.7 KB of identity data, ~2 KB of heap once used, ~35 ms to create (in the request, atomic, no failure window). Nothing in CPU, memory or latency moved between 10 and 500 merchants. 10 000 is just rows, unlike Zitadel instances (unproven at 10k).
- **What's new to own is cross-pool isolation.** It holds in every test and probe, but it rests on a pool filter in each storage query and on per-pool limits we don't have yet (the per-IP bucket and the hash slots are shared). Production would want the pool enforced structurally (a query layer, or row-level security keyed by pool).
- **Still everything h.md listed** (MFA/passkeys, email codes, reset, login page + CSRF, admin UI), now per pool, plus custom domains with passkey RP IDs. The multi-pool part is the cheap part; the login UX is the expensive part, and it costs the same with Zitadel as with this.
