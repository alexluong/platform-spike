# Review: stack c (Hono + Better Auth + Cerbos + Postgres)

Reviewed on 2026-10-11, branch `review-c`, against `ps-c` on cs-ws. Builder's claim: 341/341. After the fixes below: **346/346** (5 new regression tests), including the slow break-glass expiry test. Unit tests: 21 (was 12). Cerbos policy tests: 107 (was 104).

The patterns mostly hold. The worst problem was one nobody wrote a test for. The executor holds a DB connection for the transaction while `can()` (the PIP) borrows another from the same pool, so one user sending ~60 parallel requests hung the app for good.

## Pattern verdicts (SPEC §1)

1. **Action = unit of capability, one executor: bent.** There is one executor, and the outbox is written in the same transaction. But authorization is in two places: `authorize` (before the transaction) and guardrails in `run` (inside it; the cause of #1). `store.list` skipped the checks altogether (#3). The registry ids (`member.add`, `role.list`, `order.list`, `store.list`, …; 41) aren't the catalog ids (26), so "action id" means two things.
2. **One `can()` in AuthZEN shape: holds.** `evaluate`, `evaluateMany` and `searchResources` exist; deny reasons come from rule outputs. `subject.properties` is unused, which is the hook a per-request PIP cache would use.
3. **Custom roles are data: holds.** Merchants never touch policy. The cost: the catalog is copied into YAML by hand (one rule per permission). Now checked by a test.
4. **App DB is the source of truth: holds.** Cerbos stores nothing, so read-your-writes comes for free. The outbox is written but never consumed (nothing to sync).
5. **Three checks: bent.** The token check is only `scope=api` plus `kinds` on a few actions. Most actions have no `kinds`, so app, agent and customer tokens reach the engine, and the policy alone denies them. Relationship and condition checks are both in Cerbos and work.
6. **Tenant isolation twice: bent.** Users and agents are confined in SQL and by the policy. Apps and platform staff have only the policy (#9). Customers: no data goes to the engine; they appear as a deny-all principal for `/me/permissions` and any engine-checked route, which is fine.
7. **Composition root by hand: holds.** `main.ts` wires everything; no container, no globals. A smell: `Principal.credential` (raw bearer) travels through the kernel (#11).

## The Cerbos PIP approach

- **Correctness: good.** No cache, so a role edit or uninstall applies on the very next request. Store-scope and merchant-scope permissions are kept apart: store permissions = merchant ∪ that store, merchant permissions come from merchant-scope assignments only. A granter's access is dropped once they leave the merchant. Expiry is compared in CEL. One gap: PIP reads run outside the request's transaction (now by design, on their own pool), so guardrails can't see the transaction's own writes. No action needs them today.
- **Cost:** 3 queries per check (members, assignments ⨝ roles, resource), repeated for every `can()` in a request, plus 2 per distinct granter for agents. `evaluateMany` is batched well: one gRPC call for all of `/me/permissions` (17 actions). The waste is in reloading the subject, not in the fan-out. **Fix:** load the subject once per request. The executor already builds one `Subject` per request in `bindCan`. Have it call `pip.subject()` once and pass the result as `subject.properties`, and have the adapter use `properties` when present. That cuts `PATCH role` from 5 loads to 1. Also pass `principal.merchantId` in, so the PIP stops re-reading `members`.
- **Permission list duplicated in YAML and code.** One rule per permission, because CEL can't see the action. It is copied 2× per resource, plus the `storeActions` / `neverForApps` constants and two break-glass lists. Options, least bad first:
  1. **A CI check (done):** `ts/src/kernel/policy-sync.test.ts` fails on a missing or extra rule, on a rule whose condition names another action, on drifted constants, and on a non-`.view` break-glass action. Checked by mutation: it catches a copy-paste `order.cancel` → `"order.view" in V.granted`.
  2. **Generate the per-permission rules** from `kernel/catalog.ts`: a `pnpm gen:policy` that writes `merchant.gen.yaml` / `store.gen.yaml` (Cerbos can't include files, so the generated rules go into the policy file between markers), with CI checking the diff. Worth it once the catalog grows past ~30.
  3. Rejected: sending the action as a resource attribute (`R.attr.action`, one resource entry per action, one `actions: ["*"]` rule). It removes the duplication but breaks Cerbos's action model (outputs, audit, PlanResources per action) and multiplies resource entries.

## What I'd change in the spec

- **§1.1:** authorization finishes before the transaction opens. Guardrails become part of `authorize` (they need only input plus `can`), and the spec says `can()` must not depend on a held DB connection. #1 grows out of the spec's silence here, and stacks `a` and `b` should be checked for the same thing.
- **§5/§6:** say which actions an agent may hold. Recommend the apps' `NEVER_FOR_APPS` list applies to agents too, or that durable changes made by an agent (assignments, installs) are rejected. Also say whether app installs must re-check that the installer still holds the scopes, as agent grants do. Record the actor on assignments, installs and grants.
- **§6:** grants only to agents the granter registered (AMBIGUITIES #36). Set a maximum `expiresInSeconds`.
- **§7:** "every request under break-glass" includes list endpoints and `/me/permissions`. Say whether denied attempts are audited.
- **§7:** `merchant_suspended` goes only to the merchant's own principals; others get a plain 403/404.
- **§9:** list allowed principal kinds per endpoint (the token check), and name the 400 for out-of-range money.
- **§9:** add `GET /role-assignments` (AMBIGUITIES #11) and invitations for `member.add`, or state that consent is out of scope.
- **§10/§11:** say login hardening (rate limits, lockout) is out of scope, or require it. Say the test endpoint must not be enabled by the default compose profile outside the suite.

2. Break-glass store listing is audited.
