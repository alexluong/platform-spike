## Verdicts

### (a) The TS engine swap (d → e) vs Go's (a → b)

**Both hold "by adapter" if you count diff lines. In TS the adapter does more of the work.** Go's a → b changed no module, kernel, port or migration. The hidden costs were contracts: OpenFGA needed a single drainer, and error classification decided which events were lost (review-b). In TS, d → e changed one module line plus an engine-neutral migration, but the SpiceDB adapter now carries two things Go's kernel owns:
- **Deny reasons and the break-glass audit marker.** Go decides these in the executor with SQL prechecks; d took them from Cerbos rule outputs. e rebuilds them in the adapter from the DB (PIP), and the break-glass marker becomes an inference (#2).
- **Event meaning.** Go's events carry full state, so the adapter is a translator. d's events are ids, so the adapter has to know the app's schema: `sync.ts` reads 9 tables, Better Auth's `member`/`organization` among them.

So the port held in TS because the adapter took on read-model duties. Go's swap was cleaner because Go's kernel was designed for a stateful engine from the start (`a` came first). d's kernel was designed for a stateless one.

### (b) TS vs Go on SpiceDB (e vs a)

| | e (TS) | a (Go, main) |
|---|---|---|
| adapter (authorizer + sync + client) | 389 | 328 (`spicedb.go`) |
| schema generator | 102 | 126 |
| relay | 117 (one global lock) | 231 (consumers, per-merchant partitions from a2) |
| read-your-writes | ZedToken in the DB: holds across instances | token in process memory: one instance (known limitation) |
| SpiceDB deadline | 3 s per call | request context only |
| waiting for the drain | try-lock + poll on the relay's own pool: no request connection held, but unfair (#5) | blocks with a request-pool connection (review-a 19) |
| classification | fixed here (#1) | same FailedPrecondition bug |

- **Size: a tie.** The reconciling sync costs about what Go's full-state events cost in the modules.
- **DX: Go is better.** In TS: protobuf-ts `X.create`, oneof objects, `PbStruct.fromJson`, no exported gRPC status enum (the code compares `3`/`9`), streams buffered into arrays. Fully typed, but noisy. Go's struct literals and `status.Code` read more directly.
- **Correctness: e is ahead.** It fixed three Go gaps (multi-instance token, call deadlines, waiters holding request connections), and it shares, and here fixes, the classification bug.
- **Relay designs.** *Full-state events* (Go): one write per event, the relay knows nothing of the app schema, modules must emit complete state, and correctness depends on applying in commit order (review-a: safe only because writers hold row locks). *Reconcile-from-DB* (e): idempotent, insensitive to order when applied one after another, self-healing (any later event for the object repairs a dead-lettered one), and a full resync comes almost for free. Costs: 2–10 SpiceDB calls per event (reads before writes; `member.removed` reconciles every binding of the user), the sync tied to the app's tables, and still one drainer per object (#7). **I'd pick reconcile:** events name the object (type, id, merchant for partitioning), consumers read the truth, and a resync job reuses the same functions.
- **Cost of the DB token:** one indexed single-row `SELECT` per check call on the PIP pool. It is one global token, so every check asks for at least the latest write anywhere. Under steady writes, checks run at or near the head revision, which gives up SpiceDB's quantized cache: the same cost profile as OpenFGA's `HIGHER_CONSISTENCY`. Writes made outside the relay (zed, another service) aren't covered; my stray relationships needed 6 s to show at 5 s quantization. A per-merchant token would keep caching for untouched tenants.

### (c) Better Auth organization plugin + a relationship engine: does it fit?

**Yes. Better Auth's tables are app tables, so the engine doesn't care where membership lives.** Organization, member and invitation rows commit with the outbox row in the request's transaction (d's bridge), so membership reaches SpiceDB like an assignment does, with no second writer and no IdP consumer. The engine needs membership only for `agent_register`; permissions still come from bindings, so the org plugin's role model stays unused (as in d). The login policy reads `organization.status` from the DB directly, so suspension at login is immediate, whatever the relay's lag. All the fragility is d's (internal AsyncLocalStorage, compensating writes; review-d #1, #3), and none of it is new with SpiceDB. Compared with a2 (Zitadel organizations, identity sync as a second outbox consumer), e has one less consumer and no failure window between the IdP and the engine.

## What I'd change in the spec

1. **§1.4, outbox event shape:** an event names the object that changed (`type`, `id`, `merchantId`), and consumers read its current state from the DB. Every state change emits one, even when today's engine doesn't need it (d omitted break-glass). Require a resync path that reuses the same functions.
2. **§1.2, ownership of deny reasons and audit markers:** the executor owns them, with SQL prechecks for kind, tenant, install, suspension (`merchant_suspended`) and staff break-glass. The port returns allow/deny (plus a condition reason such as a missing context). That makes adapters truly engine-neutral, removes the PIP calls from the SpiceDB adapter (#9), and confines staff in SQL (#2; extend §1.6 "twice" to platform staff).
3. **§1 Operational rules, classification:** "permanent" means the event can never apply against the code's own schema. A missing or stale schema is transient (SpiceDB FailedPrecondition, OpenFGA missing model/store). Deploy rule: the schema is written before code that needs it runs (#10).
4. **§14 P6:** choose 503 `sync_pending` for a write whose settle fails. Measured in e: 5 s settle timeout, catch-up about 2 s after SpiceDB returns; checks fail closed meanwhile.
5. **§1 read-your-writes across instances:** a token in the DB meets the rule. State its cost (a global token ≈ head consistency) and allow a per-merchant token.
6. **§1 RelationSync contract:** an adapter may assume one drainer per object (e's reconcile and b's read-diff-write both need it). Partitions must keep each object in one partition. Waiting for the drain queues on the lock instead of polling when the relay has its own pool (#5).
7. **§11 ops:** each stack records its per-instance connection budget (sum of pools) against Postgres `max_connections` (#6).
