Shared modules and kernel not re-reviewed (review-a).

With `MAX_WORKERS=4` at load 27→42: 346/362, 16 timeouts. Every failure in every run was a 30 s test timeout during logins; no wrong answer. ## Findings, by severity

### Medium

1. **A signing key deleted in Logto kept verifying tokens until the app restarted (fixed).** `logto.go` `New`. go-oidc's `RemoteKeySet` re-fetches the JWKS only when a token names a kid it hasn't cached. Probed live: rotate the signing key (`POST /api/configs/oidc/private-keys/rotate`), delete the old one, then send a token signed with the deleted key: Logto's JWKS no longer lists it, all 3 replicas agree, and `/api/me` still answered **200**. Deleting a key is what you do after a leak, so the response to a key compromise was "restart every app instance". Fix: the key set is rebuilt after 5 min (`keySet`, `jwksMaxAge`), so the next verify fetches the current JWKS. Re-probed on the fixed build: 200 right after the delete, 401 within 5 min. Test: `TestKeySetDropsDeletedKey`. Stacks a and b use the same `RemoteKeySet` pattern and have the same hole.
2. **Every Management API call failed for up to an hour after a key rotation (fixed).** `logto.go` `api`. The admin token is cached until 1 min before its 1 h expiry, and a 401 didn't drop it. After the key delete above, every `POST /api/_test/users` returned 500 (`401 ERR_JWKS_NO_MATCHING_KEY` in the app log) and a 60-user burst got 0/60. Same with a rotated admin secret or a reset Logto DB. Fix: on 401, drop the cached token and retry once. Re-probed: user create 201 right after the key delete. Test: `TestAPIRetriesWithFreshTokenOn401`.
3. **A slow user create leaves a Logto user the app doesn't know, and the email is then stuck (not fixed).** `CreateUser` (and `CreateClient`) run outside the DB tx with a 15 s client timeout. Under load Logto took longer than 15 s: in a 60-user burst at load ~25, 3 creates timed out, the app answered 500, and Logto created the users anyway (180 `burst-*` users in Logto, 177 in the app). Those users can sign in to Logto but map to no principal. A retry with the same email gets Logto 422 `email_already_in_use` → 500, forever. Same class as review-a #12 but Logto's CPU cost makes it likely, not theoretical. Options: on 422, look the user up by `primaryEmail` and adopt it (safe only while the app is Logto's only writer, which it is here: sign-up is off); or pass our own user id (Logto ≥ 1.44 accepts a custom `id` on `POST /api/users` in OSS) so a retry is idempotent by id. Only test mode creates users today, so not fixed.
4. **Wrong passwords are a cheap CPU DoS on every replica (not fixed, ops).** Argon2 verification runs on Logto's main event loop (`results/f.md`), OSS has no rate limit, and the edge allows `/api/experience/verification/password` from anyone who can reach 8092. 40 clients × 6 wrong-password attempts (unknown emails, no credentials needed) took ~44 s through 3 replicas, and `/oidc/jwks` latency went from 12–26 ms to up to 843 ms while it ran (load ~21). Each replica handles a handful of failed attempts per second, and while it does, its token endpoint and JWKS stall too. Logto's sentinel locks an identifier after repeated failures (default policy, `sentinelPolicy: {}`), which also means anyone on the network can lock a known user out. Production needs a rate limit in front (`limit_req` per IP on the password and identification routes) and probably a CAPTCHA (Logto has Cap/Turnstile). Not added here: the suite logs everyone in from one IP.

### Low

5. **`/api` itself was proxied to Logto (fixed).** `edge/nginx.conf`: the block was `location /api/`, so `/api` (no slash) fell through to `location /` and reached Logto (404 from Koa, nothing behind it today). Now `location /api` (the longer `/api/experience…` and `/api/.well-known/` prefixes still win). Everything else held: `/API/users`, `/Api/users`, `/api%2fusers`, `/api/experience/..%2fusers`, `//api/users`, `/./api/users`, `/%61pi/users` and `;`/`?` suffixes all get nginx's 404 or Logto's sign-in SPA (the mixed-case paths: Logto's API router is case-sensitive, checked with a valid Management API token → HTML, not JSON). `/console` is the sign-in SPA's catch-all, not the console. No admin tenant through any Host (`localhost:3002`, `127.0.0.1:3002`, `f-logto:3001`): `ADMIN_DISABLE_LOCALHOST` holds. `development-user-id` header → 401 (`NODE_ENV=production` from `npm start`).
6. **Discovery reflected the client's Host (fixed).** With `TRUST_PROXY_HEADER=1` and `proxy_set_header Host $http_host`, `Host: evil.example` (or `X-Forwarded-Host`) turned `authorization_endpoint`, `token_endpoint` and `jwks_uri` in `/oidc/.well-known/openid-configuration` into `http://evil.example/…`. The `iss` stays `ENDPOINT` (tokens minted through a spoofed Host still carry the right issuer), so the verifier was never fooled; the risk is a poisoned cache or a client that follows discovery. The edge now sets `Host` and `X-Forwarded-Host` to `LOGTO_PUBLIC_HOST` (nginx template, `${STACK_F_HOST}:8092`). Re-probed: discovery ignores both headers.
7. **The seed SQL ran its INSERTs on every `up` (fixed).** `ON CONFLICT DO NOTHING` makes it idempotent on today's schema, but the INSERT still names `applications.secret` (a legacy column; the live secrets are in `application_secrets`) and 2 other tables. A release that drops or renames one of them would fail the one-shot on an *existing* stack, and `f-bootstrap` waits on it, so the app would not start after the upgrade. Now the seed checks for the client first and exits (`\if :seeded … \quit`); only a fresh install depends on the column list, and there it fails loudly. Verified both paths: restart → "client exists, nothing to do"; `down -v` → seeded, role assigned. See "The SQL seed" below for the alternatives.
8. **`CreateClient` left a live M2M app when reading its secret failed (fixed).** The second call failing (timeout, 5xx) returned an error but kept the app and its secret in Logto. It now deletes the app. Orphans from a rolled-back DB tx after a successful create remain (review-a #12, all stacks).
9. **The admin M2M secret is a constant in the repo, and `/oidc/token` is public (not fixed, spike config).** Anyone who can reach 8092 mints a Management API token (`aud https://default.logto.app/api`, scope `all`) with `psadminm2m:logto-f-dev-admin-secret`. It is useless today (the Management API is unreachable from outside, the app rejects it: wrong `aud`), but one edge rule slip turns it into full admin. Generate it per stack, as with `TEST_SECRET` (review-a #7; f's `driver-config` itself hands out nothing secret, better than a).
10. **Client IPs in Logto's logs are spoofable.** The edge appends to a client-sent `X-Forwarded-For` and Logto trusts the leftmost entry. Logto uses the IP for audit logs and passcode sending only (the sentinel keys on the user), so this is log integrity, not a bypass. Behind a single trusted proxy, `X-Forwarded-For $remote_addr` (or nginx `real_ip`) fixes it.
11. **Logto apps and secrets are never removed.** The identity port has no delete: after the suite, Logto holds 117 M2M apps for apps/agents whose rows the app may have revoked. Their secrets still mint tokens; `Verify` passes them (`client_id == sub`) and the app answers 401 or 403 from its own rows (agent grants revoked in SpiceDB, no principal for unknown subjects). Correct, but a leaked agent secret stays a valid Logto credential forever. Same in a and b. A `DeleteClient` on the port (outbox-driven) would close it.

## Token verification: tried to break it

All live against `/api/me` on the fixed build:

| token | result |
|---|---|
| user access token from the driver SPA | 200 |
| ID token of the same login | 401 (`typ` missing, `aud` = SPA id) |
| header re-written to `typ: JWT` | 401 (signature) |
| `alg: none` with the same claims | 401 |
| `sub` swapped to another id | 401 (signature) |
| Management API token (`aud https://default.logto.app/api`) | 401 (`aud`) |
| client_credentials of an M2M app that is no app/agent here (`psadminm2m`) | passes `Verify`, 401 (no principal) |
| token signed with a deleted key | **200 before the fix**, 401 within 5 min after |
| token minted through a spoofed `Host` | `iss` unchanged (from `ENDPOINT`) |

Reading the code and go-oidc v3.21: `exp` is required (a missing `exp` counts as expired), `nbf` is checked when present (Logto doesn't set it), `iss` is an exact string compare, the alg allowlist is ES384 + RS256 (Logto's two rotation choices). `typ` is read before the signature check but only acts as a reject, and the header is covered by the signature. No refresh token is issued (no `offline_access`). Key rotation propagates to all 3 replicas at once (JWKS and the signing kid checked per replica), and a token with a new kid makes the app fetch the JWKS (200 right after rotation).

The `checkClient` rule holds for what Logto can issue today: `client_credentials` exists only for M2M apps and always has `sub == client_id`; a user token from another app fails the `client_id` check (builder's live test). The one path to a user token through the login app without the user's password is **token exchange** (impersonation subject tokens or PATs created with the Management API, exchanged at `/oidc/token`): anyone with Management API access can mint `client_id = login app, sub = any user`. That is admin-equivalent access anyway, but such tokens look like real logins; if they ever matter, reject tokens with an `act` claim.

## The SQL seed of the first Management API client

What it does: inserts one M2M app (`applications` + `application_secrets`) into tenant `default` and assigns the pre-seeded role "Logto Management API access" (`applications_roles`). It runs as the Postgres superuser, so Logto's row-level security doesn't apply.

Risks: it depends on 3 tables and on the role's display name. Alterations migrate existing rows, so a seeded app survives upgrades like a console-made one; the risk is the INSERT itself, now limited to fresh installs (finding 7). Logto's docs only describe the console route (`docs.logto.io/integrate-logto/interact-with-management-api`); there is no env var or CLI.

Alternatives, none clearly better:
- **Read, don't write:** Logto's own seed creates `m-default` ("Management API access for default") in the **admin** tenant with a random secret. Reading that secret is a `SELECT`, but its tokens come from the admin tenant's OIDC, which is served only on the admin port: you'd have to run 3002 on the internal network (not published). Still a DB dependency, with broader rights.
- **Drive the console's first-run flow headlessly** against an internal-only admin port: create the first admin through the admin tenant's experience API, then create the M2M app with the console's own API. Only documented APIs, but ~3 more steps to keep working across releases.
- **Pin and test:** keep the seed, and run it against every new image tag in CI before bumping (`down -v`, `up`, bootstrap). That is the cheapest guard, and what I'd do.

## Ops and performance (load averages from cs-ws `uptime`)

- **CPU per create + login** (cgroup `usage_usec`, 60 parallel create + login + `/api/me`): Logto 3 replicas 556 ms + Postgres 121 ms = **677 ms** (load 16→22), second run 533 + 133 = **666 ms** (load 21→27). Builder: 630 ms. Confirmed. Postgres also serves the app and SpiceDB, but the app's own CPU was 11 ms per login, so it is mostly Logto's queries. Edge: 4 ms.
- **Memory:** ~310 MB per Logto replica right after the bursts (builder: ~290 MB).
- **Cold start** from `down -v` (images built): **34 s** to app healthy at load ~14 (builder 31 s). Seed path ran on the fresh DB.
- **60 parallel create + login:** 60/60 in 25 s, 57/60 in 27.5 s (the 3 = finding 3), 60/60 in 28 s; load 16–33. Builder: 12–27 s. The app-level 60-request permissions burst was not re-run (no app or kernel code changed).
- **Replicas:** consistent for everything probed. Interactions and sessions are in Postgres (the suite's logins hop replicas through nginx round-robin), a key rotation is visible on all 3 at once, and the sign-in experience is read from Postgres per request (no Redis). No sticky sessions needed.
- **Worker count:** at load 25–43 even `MAX_WORKERS=4` times out 16–31 tests; `MAX_WORKERS=2` passed 362/362 at load 37→25. On this shared VM the suite result for f is a function of the load, so I'd quote f's pass count with its load.
- Logto runs as root in its container (`svhd/logto` default). Minor; set `user:` if it ever leaves the spike.

## Verdict on Logto for the login-only role

I agree with the builder: for login only, Logto doesn't beat Zitadel or Ory. The tokens are the cleanest of the three, and I couldn't break the verifier (the two holes I found, the key cache and the stale admin token, are in our adapter, are generic, and are fixed). The case against Logto is runtime: ~670 ms of CPU per login, Argon2 on the event loop, so every replica is a few wrong passwords per second away from stalling its token endpoint. In production that means replicas + a rate limit + a CAPTCHA before it is safe on the internet. Add a SQL seed with no supported alternative, a proxy that has to hide the Management API, and branding/custom UI behind a licence since 1.45. I'd add one point to the builder's verdict: the user-create path is not idempotent, and Logto's slowness makes that bite in a plain 60-user burst (finding 3). Choose Logto only if per-merchant SSO, invitations or its hosted sign-in UI become requirements, and then budget for the rate limiting and the licence.
