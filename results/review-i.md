# Review: stack i (stack a with one Zitadel instance per merchant, the app as gateway, + SpiceDB)

Reviewed 2026-10-19, branch `review-i` (from `stack-i` `b0e85aa`), against `ps-i` on cs-ws (~2400 → 2950 instances). Read SPEC §16, `results/i.md`, `results/zitadel-instances.md`, `results/review-a.md`, `results/review-h2.md`, the adapter (`go/internal/adapters/zitadel`: gateway, instances, system, verify, schema), the shared module changes (migration 003, core principal/executor, platform, merchants, invitations, agents, orders, new `customers`, outbox relay), the composition root, compose and the driver. Probed the running stack three ways:

- `stacks/i/review-gateway.sh` (curl on cs-ws): paths, pool-selecting headers, Host variants.
- `conformance/review-i/probe.test.ts` (vitest, `--config review-i/vitest.config.ts`): cross-pool codes, auth requests, intents, tokens; Sign in with Shop edges; login CSRF; disabling identities (`I_REVIEW=1`).
- `go/cmd/i-review` (review tool, not part of the app): Zitadel calls with the app's **provisioner system key** from a container on the stack network, i.e. what a control plane, or anyone who steals the key, can do.

**Suite after fixes:** **401/401** (362 core + 39 multi-pool; 30 `idp-tenancy` skipped), 188 s, stack rebuilt from this branch (`up -d --build`, 2950 instances at the end), host load 2–20. An earlier run on the same build at load 58–72 (other workspaces' benches) was 398/401: two guardrail tests hit the 30 s timeout and rule 9 saw one merchant still `provisioning` at 60 s (provisioning p50 13.7 s / p95 22 s during that run, no provisioning errors in the log). That's load, not a finding (brief). Probes 4/4. `go test ./...` passes (new: `TestGatewayRouting`, `TestTokenFits`).

The builder's isolation holds: every cross-pool attack I tried failed, mostly because Zitadel instances share nothing per merchant (keys, users, sessions, codes, intents), and the gateway's header handling is right. What the review found sits around the instances: what holds god-mode keys, what Zitadel may dial, what disabling someone does, and MFA.

Checked and fine:
- **Headers and Host:** client `x-zitadel-instance-host`/`-public-host` (any case), `X-Forwarded-Host`, `Forwarded`, `x-zitadel-forwarded` never change the instance (issuer stays the directory's); `Connection:` hop-by-hop tricks change nothing; upper-case Host → same pool; trailing dot, no port, wrong port, two labels, Zitadel's own instance domain, HTTP/1.0 without Host → API or 404. An absolute-URI request uses the URI's host as Go does (the client just asked for that pool). The proxy deletes every `x-zitadel-*`/`x-forwarded-*`/`forwarded` and sets both headers from the directory, so Zitadel sees exactly one.
- **Zitadel isn't reachable from the LAN:** only 8096 is published; Postgres, SpiceDB and Zitadel aren't. Admin, management, system, user v2, console, debug → 404 through the gateway (direct and via traversal).
- **Cross-pool:** M1's auth request at M2's login → 400; M1's code at M2's token endpoint (M2's and M1's client id) → refused, and still redeemable at M1; M1's access token at M2's userinfo → 401, at M2's merchant → 403/404; an ID token as bearer → 401; M1's Shop intent at M2's `idp/done` → 401 (`Intent has not succeeded`); a staff-scoped auth request taking the Shop path → Zitadel refuses to finalize (`User is no member of the required organization`).
- **Verifier (P7):** issuer allowlist = directory (unknown or provisioning → 401, no key fetch for unknown issuers); RS256 only; `aud` = the pool's login project; access-token shape (`client_id`, none of `at_hash`/`nonce`/`azp`/`amr`); client = the pool's login app, machine clients only in the platform pool. The per-merchant `shop-*` confidential apps can't mint API tokens (wrong client).
- **Suspension and kept keys:** the last good JWKS kept for a blocked instance only lets its tokens verify, and the app then answers 403 `merchant_suspended`; nothing can be minted while blocked (gateway refuses from the directory commit, Zitadel's limit follows). Suspend/reinstate vs provisioning is race-free (row lock + desired state applied at the end).
- **Provisioning:** no double instance: the instance domain is deterministic and globally unique in Zitadel, so a retry after a lost `_create` response gets 409 and then finds it by search. The merchant row and the outbox row commit together; a rolled-back create leaves nothing.
- **Linking:** never by email (auto-linking off; the local customer with the buyer's email stays apart: suite rule 7); one link per instance and IdP.

## Recommendations

### System keys (#1): split by who needs what

| service | exposure | key / membership | needs it for |
|---|---|---|---|
| **API** (modules, gateway, verifier) | internet | **none** for logins/verification: JWKS is public, routing is the directory. Machine clients for apps/agents: move to the control plane over the outbox, or a key scoped to the platform instance only (`MemberType: IAM`, that instance's id; check the scoping on the current Zitadel) | — |
| **control plane** (outbox consumer: provisioning, block/unblock, delete, OIDC settings, Shop disable propagation) | internal only | `provisioner`: SYSTEM_OWNER (create, limits, delete) + IAM_OWNER for the template steps | instance lifecycle |
| **login UI, merchant/Shop pools** (Login UI v2 or ours) | internet, behind the gateway | `login`: IAM_LOGIN_CLIENT, scoped to platform + tenant instances if the version supports instance-scoped memberships | sessions, finalize, intents |
| **login UI, workforce** | staff only | its own login key, or workforce on **its own Zitadel deployment** (the model's blast-radius reason for a separate instance only holds if no key spans both) | staff logins |

Keys from a secret store, mounted read-only per service (not one `0644` volume), rotated by adding a second system user and retiring the first. Zitadel itself needs only the `.pub` files.

### MFA (#3): where the check goes

1. **Login UI is the enforcement point** (Zitadel won't do it on the Session API): after the first factor, read `GET /v2/settings/login?ctx.orgId=…` and finalize only when the session has the required second factor (`webAuthN` with `userVerified`, `otp*`), always for workforce and platform accounts (and tenant staff in this spike's layout). Our stand-in and any custom UI must do the same; stock Login UI v2 already does.
2. **App-side belt for staff pools:** the access token carries no `amr`. Either add a claim through an Actions v2 `preaccesstoken` function (check that it receives the session's auth methods; if not, the login UI records them in session metadata the function can read) and check it in `Verify` per pool, or use introspection for staff tokens. Then drop the `len(cl.Amr) > 0` rejection, which would refuse such tokens.
3. With it: a lockout policy per pool (or rate limits per pool in the login UI; lockout alone lets anyone lock out a known email).

## Pattern verdicts

| pattern | verdict |
|---|---|
| instance per merchant, picked by `x-zitadel-instance-host` from a directory | **works and isolates well**: separate keys, users, sessions, codes and intents per merchant; every cross-pool attack failed at Zitadel before the app even looked |
| the app as gateway (public host = issuer, header stripping, path allowlist) | **right**, now with clean-path enforcement; in production a separate edge service, so the API process doesn't proxy Zitadel |
| subject qualified by pool + home merchant = issuing pool | **keep both** (the second added here); together they make the issuer the only thing that picks a principal's pool |
| last good JWKS kept in the directory | **good** (static stability, suspended tokens → 403 not 401); add a `deleted` pool status so it can't outlive offboarding |
| async provisioning via outbox, each step resumable | **sound**, but every "ready" is a probe of the real path, and under load it takes 10–20 s; the cost h2 doesn't have |
| Shop as a generic OIDC IdP between instances of one deployment | **works**; needs an egress path that doesn't open private ranges (#2), browser binding at the success URL (#10), and disable propagation (#4) |
| system API users for everything | **the weak point** (#1): convenient (no per-instance credentials), but the blast radius is the deployment |

## Verdict: i vs h2 for this model

**Both carry the model; neither is clearly better, and they fail in different places.**

- **Isolation:** i is stronger by construction. Per-merchant instances share nothing a bug in our code could mix up; h2 needed composite keys and a lint (review-h2 #2) to get there. In i, no cross-pool attack touched the app's code at all.
- **Blast radius:** i is weaker as built. One system key spans every pool including workforce (#1), and federation wanted a hole in the SSRF list (#2, fixed). h2 has one `ISSUER_SECRET` for all pools, the same shape. Both need the split.
- **Cost and operations:** h2 wins: provisioning in the merchant's transaction (~35 ms, no states) vs 1–20 s of eventually-consistent steps; no idle projection tuning; restart time and event-store growth with instance count are i's alone; 10k instances is still unmeasured.
- **Login features:** i wins: MFA, passkeys, invites without SMTP, per-merchant SMTP/branding/policies already exist. But MFA still needs our login UI to enforce it (#3), so the gap is smaller than it looks. h2 has to build and review each feature.
- **Lifecycle gaps** (disable propagation, offboarding) are in both, for the same product reasons.

**Pick i if login features and owning no auth server matter more than per-merchant ops cost**, and only with the key split, short token lifetimes, a real 10k bench, and the egress fix. With the 2026-10-19 decision (tenant instances hold customers only, staff on the platform instance), i's per-instance cost buys only customer login. That makes **h2-style rows the cheaper home for tenant customer pools**; Zitadel stays a good fit for the few platform-level pools (workforce, platform accounts, Shop). That hybrid is worth putting to the model before choosing one stack wholesale.
